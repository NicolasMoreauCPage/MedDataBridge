Intégration IHE PAM (Profil France) — Documentation technique complète

Objectif

Ce document décrit de manière exhaustive l’intégration des messages IHE PAM (ADT, ZBE, MRG, etc.) dans MedData_Bridge, en conformité avec les spécifications IHE France. Il s’adresse aux experts de l’interopérabilité, développeurs et intégrateurs qui doivent maintenir, étendre ou valider le pipeline PAM.

1. Segments HL7 lus et mapping

  • MSH : Validation complète selon IHE France (séparateur, encodage, type, trigger, version, control ID, processing ID).
  • EVN : Cohérence EVN-1/MSH-9.
  • PID : Validation stricte de tous les champs clés (PID-3, PID-5, PID-7, PID-8, PID-11, PID-13, PID-18, PID-32). Mapping vers Patient.
  • PV1 : PV1-2, PV1-3, PV1-10, PV1-19. Mapping vers Venue et Dossier.
  • ZBE : Extension France pour mouvements. Mapping vers Mouvement.
  • MRG : Fusion d’identités. Utilisé pour A40.
  • NK1 : Contacts. Mapping vers PatientContact ou VenueContact.
  • PD1 : Informations complémentaires patient (optionnel).

Les usages, cardinalités et listes de valeurs sont conformes aux tableaux des specs IHE France.

2. Gestion des identifiants et namespaces

  • PID-3 : CX, format ID^^^SYSTEM&OID&ISO^PI, validation structure, unicité, longueur EI-1.
  • PV1-19 : identifiant de séjour (CX).
  • ZBE-1 : identifiant mouvement (ID^AUTHORITY^OID^ISO).
  • MRG-1 : identifiants à fusionner (CX répétés).
  • Namespaces extraits et validés selon les specs.

3. Modèle relationnel et parentage

  • Patient → Dossier → Venue → Mouvement
  • Parentage résolu par identifiant (PID-3, PV1-19, ZBE-1).
  • Annulation, fusion, update : rattachement dynamique selon trigger et segments.
  • Contacts (NK1) rattachés au patient ou à la venue selon la date/heure.
  • Transactions SQLModel, rollback en cas d’erreur.

4. Algorithme de traitement et transactionnalité

  • Pipeline principal : on_message_inbound_async (validation, parsing, routage, journalisation, transaction).
  • Validation structurelle, parsing, mapping, validation métier.
  • Routage métier via IHEMessageRouter selon le trigger.
  • Gestion des annulations, fusions, mises à jour partielles, fallback.
  • Log détaillé, création de parents virtuels si nécessaire.

5. Règles métier par trigger

  • A01/A04/A05/A06/A07 : admission, pré-admission, changement de classe.
  • A02/A12 : transfert, annulation de transfert.
  • A03/A13 : sortie, annulation de sortie.
  • A11/A23/A38 : annulation admission/enregistrement/préadmission.
  • A21/A22/A52/A53 : permission, retour, annulation.
  • A40 : fusion d’identités (PID/MRG).
  • Z99 : mises à jour partielles, tolérance sandbox.
  • Validation stricte des transitions (ordre logique, cohérence temporelle).

6. Cas d’erreur et diagnostics

  • Identifiant manquant : log, rejet, fallback.
  • Parent manquant : report, création de parent virtuel.
  • Import incomplet : log, rollback transaction.
  • Collision/incohérence : log, création de lien virtuel, rejet si non résoluble.
  • Annulation sans mouvement cible : fallback sur dernier mouvement.
  • Erreur de validation IHE France : log, rejet ou warning selon configuration.

7. Tests de validation et régression

  • Validation roundtrip admission → transfert → sortie → annulation.
  • Contrôle des transitions et des identifiants.
  • Utilisation de jeux de données de test pour tous les cas d’erreur.
  • Scripts : scripts/validate_pam.py, rapports reports/pam_import_report.json.
  • Tests unitaires et d’intégration dans archives/tests/ et pam_archive_dst/.
